Parquetry¶

Parquetry reads and writes Apache Parquet and GeoParquet files from Java, without Hadoop and without parquet-java. Give it a file and a filter, and it returns the matching rows. The file can sit on a local disk, an HTTP server, Amazon S3, Azure Blob Storage or Google Cloud Storage, and Parquetry fetches only the parts of it needed by the query.

Parquetry is a small library. parquetry-core and its dependencies add 20 jars and 12 MB to an application. It decodes Parquet inside the JVM, with no native engine and no external process. In a container, it sizes its memory from the memory limit of the container.

Why Parquetry? compares it with the other ways of reading Parquet from Java, and says when another tool fits better. Getting started adds Parquetry to a Java project and runs a first filtered read.

What you can do¶

  • Read Parquet files from a Java application

    Add one dependency and read a file with a filter, from a server, a desktop application or a command line tool. Rows come back as records or as columnar batches. The JOSM GeoParquet plugin reads GeoParquet files this way in the OpenStreetMap editor.

    Getting started then Read records

  • Write Parquet and GeoParquet files

    Write files with flat and nested columns and GeoParquet metadata, laid out for selective queries: sorted by location, with a page index and bounding box columns.

    Write files then Lay out files

  • Query a remote file by bounding box

    Give a read a bounding box, and it returns the rows whose geometry has a bounding box overlapping it. The read fetches the parts of the file able to hold such rows, and leaves the rest on the server.

    Cloud storage then Filter by location

  • Read within a container's memory limit

    Parquetry reads the memory limit of the container at startup and derives its native memory budgets from it. Concurrent reads share these budgets, and a full budget slows a read down instead of killing the process.

    Tune memory then Memory

  • Hand rows to an analytics engine

    Export a read as an Arrow IPC stream, or through the Arrow C Data Interface, and query it with DuckDB or Python. Parquetry reads and filters, and the engine joins and aggregates.

    Arrow interop

  • Serve GeoParquet from GeoServer

    A GeoTools data store publishes GeoParquet files as map layers. GeoServer Cloud 3.1.0 and newer include it and enable it by default, and a plugin adds it to GeoServer.

    GeoTools and GeoServer

Selective queries read little¶

A Parquet file stores its rows in blocks called row groups. Inside a row group, the values of a column sit together in a column chunk, cut into pages. The footer at the end of the file describes the row groups and records the minimum and maximum of their column chunks. A page index, when the file has one, records the position, minimum and maximum of the pages. A bloom filter, when the file has one, tells whether a value may appear in a column chunk.

Parquetry reads this metadata before it fetches any data, and skips the parts of the file unable to match the filter. The diagram shows a small bounding box query on a file sorted by location.

The levels run in this order:

  1. The statistics in the footer rule out row groups.
  2. The GeoParquet 2.0 geometry statistics, also in the footer, rule out the row groups whose geometries lie outside a bounding box.
  3. The page index rules out pages in the row groups left.
  4. Bloom filters rule out the row groups lacking the value of an eq or in filter.
  5. The read fetches the pages left, of the columns needed by the query, and tests their rows one by one. It returns the matching rows only.

A GeoParquet file written by Parquetry has a page index and bbox covering columns, four columns holding the bounding box of each geometry. For a small bounding box over such a file sorted by location, the statistics of the covering columns rule out the row groups far from the box. Their page index rules out the pages far from it in the row groups left, and the read fetches the few pages near the box.

The footer is read once per file. The page index and the bloom filters are read only for the row groups left by the levels before them. The levels work from the metadata of the file, and a file without it is pruned less. A read learns the pages of a file without a page index from their headers, and later reads of a row group prune pages with them (Without a page index). The per-row test keeps the result exact. Filter rows and Filter by location show the filters, and The read path follows a filtered read through these levels.

How it is built¶

Parquetry is a clean-room implementation of the Parquet format in Java: it depends on neither Hadoop nor parquet-java, and it runs no native engine. It reads files through tileverse-storage, and its architecture diagrams show the modules and how a read flows through them. Format support lists the Parquet and GeoParquet features read and written by Parquetry.

Status¶

Parquetry has not reached 1.0, and its API may still change before then. The stable parts are ready for production use. The experimental parts work, but their behavior is still changing.

Area Module Status
Reading Parquet files, with filter pushdown parquetry-core stable
Writing Parquet files, Parquet 2.0 by default and 1.1 on request parquetry-core stable
GeoParquet 1.x and 2.0 metadata, spatial filtering parquetry-core stable
Multi-file datasets: a directory or a glob of files read as one dataset parquetry-catalog stable
GeoTools data store for GeoParquet parquetry-geotools stable
Export to Arrow: Arrow IPC streams and the Arrow C Data Interface parquetry-arrow stable
Reading Apache Iceberg tables parquetry-iceberg experimental
Reading STAC GeoParquet collections parquetry-stac experimental
The par command line tool par experimental

Two supporting modules have no status of their own. parquetry-avro reads and writes Avro container files, the format of Iceberg manifests and manifest lists. parquetry-jackson renders the rows of a read as JSON.

Part of the Tileverse ecosystem¶

Parquetry is part of Tileverse, a set of Java libraries for cloud-native geospatial applications. Its storage layer, tileverse-storage, provides the byte-range reads and the caches used by Parquetry.
